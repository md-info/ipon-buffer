# Architecture and production boundaries

React/TypeScript renders the real FastAPI API through the local Vite proxy. Pydantic validates requests. Pure Python engine functions use integer minor units, Fraction/Decimal ratios, immutable inputs, and injected dates. SQLite/SQLAlchemy stores mock balances, confirmed plans, scope expiries, derived summaries, replay records and a SHA-256 audit chain. A process lock plus transaction serializes this single-process demo. Browser tokens remain in memory; the server stores their hashes. Refresh starts a new demo rather than resuming the old one.

The engine receives trailing observed features, the confirmed essentials plan, balances and the selected income event. It protects a horizon inferred from observed income gaps and the user's expected date, includes due bills, adds a 10% reserve margin, then applies surplus capture, an income-event cap, buffer target, rounding and minimum-transfer constraints. Zero is a valid recommendation. A transfer consumes a freshly generated recommendation and rechecks state. Idempotency keys bind an exact request fingerprint to one result. Withdrawal transfers funds; simulated payment is a separate expense.

AI text goes only to a configured loopback service. The model returns a bounded JSON proposal. Schema, amount, currency, date and excerpt checks run before review. Parsing cannot change plans or balances. A reviewed apply request needs the originating session, a current version and a draft younger than five minutes. Revocation/discard invalidates an in-flight request. The model never sees transaction history, credentials, transfers or ledger tools. Source excerpts cannot prove semantic correctness, so human review remains necessary. Actual local inference has been tested; reports/ai_evaluation.md documents substantial semantic errors and a failed quality gate.

FastAPI serves schemas at http://127.0.0.1:8000/docs and /openapi.json. The persisted docs/openapi.json is exported from this build. Main routes are under /api/v1: sandbox/start/reset, consents, summary, plan, recommendation, buffer/transfer, buffer/withdraw, sandbox/pay-emergency, assistant/parse/apply/draft, privacy/data and audit.

This is a local prototype, not deployable banking software. Mock partner logic lives in the API state boundary. A real partner adapter must replace it with transaction reconciliation, durable ledgers, independent identity/authorisation, key management, operations, incident response and retry semantics agreed with the partner. The current process lock does not coordinate multiple workers. Demo sessions have no production account recovery, global abuse protection or retention scheduler. There is no live deposit, interest, insurance, guarantee, or partner contract.

Replication to another market requires currency exponent/rounding configuration, reviewed translations, bill/income conventions, partner integration, local research, and legal/security review. Synthetic IDR/VND arithmetic tests do not establish readiness in those markets. English is the implemented baseline; Taglish comprehension has not been validated.

Drafts additionally pass assistant/grounding.py: limited source-evidence checks can clear unsupported dates, amounts and recurrence, filter income-like bills and known unsupported requests, and require manual budget-inclusion choice. These checks never create replacement fields. Their limitations are documented in reports/ai_grounding_evaluation.md. Caller-supplied evaluation metrics may retain raw proposals only for explicitly synthetic evaluation; ordinary app calls do not request those metrics.
